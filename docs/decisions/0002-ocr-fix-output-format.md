# 0002. OCR 修正的输出格式：自定义 `N: 文本` vs JSON

> 状态：open（未决——只记录问题与讨论点，不做选择）
> 日期：2026-11-25
> 关联：`packages/llm/src/ocr_fix.rs`（`parse_fix` / `build_ocr_fix_system_prompt`）
> 触发：讨论用提示词要求模型输出哪种格式更合适

## 背景与问题

`sf_ocr_fix` 让 LLM 修正一段 OCR 文本，输入是编号行（`1: 文本`），提示词要求输出 `N: 文本`。
要决定的是：**用提示词要求哪种输出格式**——继续用自定义的 `N: 文本`，还是改用 JSON。

这里讨论的是「用提示词要求格式」，不是 `response_format` / tool 等参数约束——当前使用的
模型端点不支持响应格式参数。两个选项都只靠提示词驱动。

## 观察到的行为

实测（2026-11-25）：期望 23 条，模型只回了 2 条：

```
2: 这蜜饯是太医院特意针对此药调配的
9: 啊切
```

`finish_reason=stop`（非截断）。模型把提示词里「没有错误的行保持原样」理解为「只输出有改动的
行」——这是更智能的模型给出的更智能的回答：用行号精确指出 2 处修正，不必把 21 条无误的原文
再抄一遍。

这种「只给必要信息、省略无变化部分」的回答称为**压缩格式**（compressed output）——它是相对
「把每条都原样列出」的完整格式而言的，信息无损，只是去掉了冗余。相应地，解析侧已改为接纳
压缩格式（出现的行号覆盖原文，未出现的保持原文，`parse_fix`）。

## 术语：为什么叫「压缩格式」

概念上（人人都清楚，不展开）：数据稀疏 = 大量默认值重复 = 冗余的一种；只存非默认值就是
去掉这层冗余、无损还原，属于最简单的一类压缩。稀疏存储是压缩存储的最简单形式，不是并列的
另一类。

**用词理由**（这才是本文选词的动机）：「稀疏存储」「稀疏格式」读起来容易歧义——「格式」一词
既有**数据结构**的意思（数据长什么样），也有**存储格式**的意思（怎么编码存放），配上「稀疏」
更混。因此本文统一用**压缩格式**，读起来指向明确：把冗余压掉后的输出形状。

> 本文「压缩格式」=「只列改动项、未列出的保持原文」的输出形状，以及 `parse_fix` 的接受语义。

## 两个选项

| 选项 | 依据 | 顾虑 |
|---|---|---|
| A. 自定义 `N: 文本` | 实测模型输出格式完全正确，格式遵循没出问题；改动最小 | 自定义格式在模型训练数据里少，理论上更易出现格式漂移（如 `**2.**`、`2 - `） |
| B. 用提示词让模型输出 JSON | JSON 是模型训练数据中大量出现的格式，格式遵循可能更稳；结构化解析（serde）不用手写行解析 | 模型有时包 ```json 代码块要剥壳；多一层 token 开销 |

两种格式下，模型都可以给出压缩格式（只列改动项）——这是模型的智能行为，不是某种格式的缺陷。
