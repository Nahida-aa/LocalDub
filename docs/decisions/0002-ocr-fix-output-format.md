# 0002. OCR 修正的输出格式：自定义 `N: 文本` vs JSON

> 状态：proposed（讨论中，暂保持 text，不做选择）
> 日期：2026-11-25
> 关联：`packages/llm/src/ocr_fix.rs`（`parse_fix` / `build_ocr_fix_system_prompt`）
> 触发：实测模型在 23 条修正中只输出了 `2:` / `9:` 两条，其余未输出

## 背景与问题

`sf_ocr_fix` 让 LLM 修正一段 OCR 文本，输入是编号行（`1: 文本`），提示词要求的输出也是
`N: 文本`。原 `parse_lines` 要求「解析出的行数恰好等于输入行数」，否则整批回退原文。

实测（2026-11-25）：期望 23 行，模型只回：

```
2: 这蜜饯是太医院特意针对此药调配的
9: 啊切
```

`finish_reason=stop`（非截断）。失败日志见 `ocr_fix.rs` 的解析失败 WARN。

**关键认定：这不是失败。** 模型把提示词里「没有错误的行保持原样」理解为「只输出有改动的
行」，给出了稀疏但语义正确的回答——它用行号精确指出了 2 处修正。问题在解析侧：把「缺失的
行」当成错误，而非「无误、保持原文」。

## 当时的想法（选项）

讨论的是**输出格式本身**用哪种，与这次稀疏行为无关（哪种格式都必须处理稀疏）：

| 选项 | 依据 | 顾虑 |
|---|---|---|
| A. 保持自定义 `N: 文本` | 实测模型输出格式完全正确（`2:` / `9:`），格式遵循没出问题；改动最小 | 自定义格式模型训练数据里少，理论上更易出现格式漂移（如 `**2.**`、`2 - `） |
| B. 用提示词让模型输出 JSON | JSON 是模型训练数据中大量出现的格式，格式遵循更稳健；结构化解析（serde）不用手写行解析 | 同样会有稀疏输出（只输出改动的 key），仍要接纳；模型有时包 ```json 代码块要剥壳；多一层 token 开销 |

注意：这里讨论的是**用提示词要求格式**，不是 `response_format` / tool 等参数约束——当前使用的
模型端点不支持响应格式参数。所以两个选项都只靠提示词驱动。

## 验证

- 源码核对：`parse_lines` 原要求行数恰好相等（`ocr_fix.rs`，已改为 `parse_fix`），失败时整批
  回退（`sf_ocr/ocr_fix.rs` 的 WARN 分支）。
- 实测：`finish_reason=stop`，模型只输出 2/23 行，格式正确。
- 未验证：JSON 提示词在本任务上的格式遵循率——没有对照实验，不假设它更好。

## 决策

**暂不做格式选择，保持 text（`N: 文本`）。** 当下只修正解析语义：接纳稀疏——出现的行号覆盖
原文，缺失的行保持原文（`parse_fix`，已实施）。JSON 作为备选留在本文，触发条件见下。

## 后果

- 稀疏、密集两种输出都能正确处理；id 越界/重复/无有效行才报错。
- 格式选择这件事没有被解决，只是被推迟。
- 若将来出现**格式漂移**（模型输出 `**2.**` 等导致行解析失败），或需要更强的结构化约束，
  再重新评估选项 B——那时才需要对照实验验证 JSON 在本任务上确实更稳。

## 重新评估的触发条件

- 行解析因格式变体频繁失败（而非稀疏）；
- 输出需要表达更复杂的结构（不是单纯的 id → 文本）；
- 换用的模型端点开始支持 `response_format`，使选项 B 从「只靠提示词」升级为「有 schema 约束」。
